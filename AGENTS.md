# AGENTS.md — maintaining this collection

Instructions for any agent editing this repository (Claude Code reads it through `CLAUDE.md`). Readers who install the skills never need this file; it is how the collection stays good.

## What this is

Agent skills for building and shipping apps with coding agents — Claude Code, Codex, Cursor, Grok and the rest. Public and free for everyone (owner, `2026-10-28`). Each top-level folder is one **plugin**, a pack for one job; each pack holds skills (`skills/<name>/SKILL.md`) and no commands: a workflow the user starts is a skill marked user-invoked (rule 7), because Codex does not load plugin commands (`2026-10-27`, Codex CLI 0.159.0). `.claude-plugin/marketplace.json` lists the packs. `README.md` is the reader's page.

## Rules for every skill

1. **A skill is general guidance read by strangers.** A product appears in it only as an example, named by kind ("a live Q&A product", "a monitoring product"). Never a product's name, its repository, commits, release codes, ids, listing ids, account names, a path on the author's machine, a secret, or private infrastructure. What is true of one product belongs in that product's repository. **One exception, by the owner's decision (`2026-10-27`):** the author's own monitoring service, Staygreen, is named in the `uptime-monitoring` skill's adapter folder and in that skill's line in `app-stack/README.md` only, each with a disclosure; `LEAK_EXCEPTIONS` in `tools/validate.py` allows that name in those two places, and in this rule, and nowhere else. **Every file here is public**, so the leak check reads all of them, not only the skills; the private names it looks for are listed in `tools/leaks.local.txt`, which is never committed, because a public list would publish them (`2026-10-28`, going public: `sources.json` and the validator's own list carried private repository names that a check of the skills and READMEs never read). Any further exception needs the owner's word and its own entry there.
2. **Keep the receipts.** A rule that came from an incident keeps its date and what happened (`2026-09-16`, a review round found …), with the product named by kind. The receipts are why a reader trusts the rule; never strip them to save space.
3. **Date what a platform did or required** ("read on 2026-10-23", "observed in"), because vendors change without notice. When one changes, correct the line; never leave the old one beside the new.
4. **Cross-reference by skill name** — "the `release-gate` skill", "`grok-agents` § Triage" — and write the call out wherever one skill needs another: "apply the `document-app` skill". A user-invoked skill can't be loaded by an agent, so it is named by what the user types: "type `/ai-shipping:ship-check` (Codex: `$ai-shipping:ship-check`)", never "the `ship-check` skill" (`tools/validate.py` fails on that). Never by a path into another repository or a section of another repository's instructions. A product's own files are named generically ("the product's agent instructions", "its backlog"), and a skill that relies on one says in its own words what that file holds. **No skill assumes the reader has the template these skills came from**: no "the template", no `AGENTS.md § <n>`, no table translating a template's paths. A reader has their own repository and nothing else (owner, `2026-10-25`: universal and self-contained, because the skills are shared with others). A receipt names its product by kind ("a monitoring product"), not by what it was built from. `tools/validate.py` fails on the first two.
5. **Self-contained.** A skill must work when its folder alone is copied into `.claude/skills/` or `.agents/skills/`. Scripts are referred to as `<skill dir>/scripts/…`, never `~/.claude/skills/…`. A skill may point to another skill in this collection by name; it must not need one to make sense.
6. **The owner is the reader.** Where a source skill carried its author's taste ("the owner's standing preferences"), it stays only as a labelled example the reader replaces with their own.
7. **Frontmatter:** `name` equals the folder name. **The description of a skill an agent can load on its own is always in the agent's context, so it starts with the trigger, in the words a user would type, then says in a clause what the skill does**, with no inventory of contents (that is the body's job): at most 300 characters each and 6,000 for all of them together. Count tokens by measuring, not by characters ÷ 4: with their names, the listing runs about 2.8 characters a token (`2026-10-27`: 5,576 characters of descriptions cost 2,423 tokens a turn in Claude Code). A crowded setup cuts descriptions to a budget from the end, so the trigger goes first (`2026-10-27`: Claude Code 2.1.311 with this collection and a user's own skills logged "Skill listing over budget… descriptions will be truncated" at 30,000 characters; Codex CLI 0.159.0 cut the longest description mid-word). **A skill the user starts** (a whole session's work, or a moment only the user picks) carries both flags: `disable-model-invocation: true` in `SKILL.md` for Claude Code, and `agents/openai.yaml` with `policy: allow_implicit_invocation: false` for Codex; its description is then out of context and may run to 1024 characters. `python tools/validate.py` checks all of it.
8. **A rule a test or script can hold gets one.** Prose obligations decay; code paths don't.
9. **Every skill says how to tell it worked**: a `## How you can tell it worked` section, one or two sentences of evidence a reader can check, not a restatement of the steps. `tools/validate.py` fails without it.

## Where each skill came from, and keeping up with it

Many skills began as copies or extractions from other repositories. `sources.json` records, for each one, the upstream repository, the commit it was taken at and the paths it came from. Skills taken from the author's private repositories, and the products below, are recorded the same way in `sources.local.json` beside it, which is never committed: the repository is public, and those repositories' names and layouts are not. `tools/check_sources.py` reads both, and reports the run as incomplete when the local file is missing. **This repository is the master for its own text**; upstreams keep evolving, so:

- `python tools/check_sources.py` lists every upstream commit since the recorded one that touched a skill's source paths. Port what is a lesson for everyone, then move the recorded commit. A change deliberately not ported gets a line under the skill's `skipped`, with the reason, in the file that records the skill: a private upstream's skip, like its skill, never goes in `sources.json`. An upstream the skills were copied from once, and are not kept in sync with, carries `"tracked": false`: its entries record provenance and the tool skips them.
- A lesson learned here that matters upstream (the free `pm-skills` catalog, or a template that still vendors the skill) is sent there the same day.
- **A request the collection decides not to take** (a skill, a pattern, a change of approach) gets an entry in `rejected.md`, beside `sources.json`: the date, the request, rejected or deferred, the reason, the evidence and who decided. An upstream change not ported stays with the skill's record (`skipped`). Read `rejected.md` before proposing a new skill; reopen an entry only with new evidence.
- **Products are where most lessons are learned, and this collection is their one master.** A product records an incident in its own docs. Its general lesson is ported here, and the product's vendored copies are refreshed from here; nobody edits a vendored copy and hopes it travels back. `sources.local.json` § `products` lists each product with the commit it was last harvested at. `python tools/check_sources.py --harvest --bodies` lists every product commit since then, because commit bodies hold most receipts, and marks those that touched process docs. Run it at each product release, port what a stranger would need, then move `harvested`. (`2026-10-25`: a product's four-day build produced about 140 lessons in its docs and commits while its skill copies stayed byte-identical, so tracking the copies alone missed all of them.)

## Before a commit

- `python tools/validate.py` passes.
- New or renamed skills are listed in their plugin's `README.md` and in the root `README.md`.
- Commit messages through a heredoc (`git commit -F -`), never `-m "…"`: backticks inside `-m` are command substitution and vanish silently.
